# Мобильное приложение (Android)

> Документ описывает мобильный клиент vibe-chat для Android. Продуктовая и архитектурная правда — в `Docs/concept.md`; этот документ конкретизирует её для мобильной платформы. При противоречии приоритет у концепции.

## 1. Обзор

Мобильный клиент — **не отдельный продукт, а вторая площадка того же мессенджера**: тот же бэкенд, тот же REST/WS API (`/api/v1`), тот же Keycloak и тот же Silo. Никаких отдельных мобильных эндпоинтов на MVP — только то, что уже существует, плюс транспорт push-уведомлений (§3.5).

- Целевая ОС: **Android 13+ (API 33)**, `targetSdk` — актуальный стабильный (35)
- Дистрибуция на MVP: **APK напрямую** (sideload / MDM), Google Play не используется → требования к релизу упрощены (нет Data Safety, privacy policy Play Console; подпись — self-signed)
- Мобильный клиент ходит на тот же стенд (`merch-vibe.ru`): API/WS через `/chat`, вложения через `/vibe-files/`, KC через `:8444` — конфигурируется на этапе каркаса (как `VITE_*` у веба)
- Язык приложения и документации — русский

## 2. Стек

Зафиксировано:

| Компонент | Решение | Обоснование |
|---|---|---|
| Фреймворк | **React Native + Expo** (development build, не Expo Go) | Пуши и нативные модули требуют dev build; Expo Go не подходит |
| Язык | TypeScript | Единый со `frontend/` |
| UI | React Native компоненты (нативные стили Android) | Tailwind/shadcn — web-only, на мобильном не переиспользуются |
| Data layer | **TanStack Query (REST-кэш) + Zustand (WS-состояние)** | Как в `frontend/` — одинаковые паттерны обеих площадок |
| Типы API | Копия контракта в `mobile/src/api` на старте; при первом расхождении — вынести общий workspace-пакет `packages/api-types` | Минимум инфраструктуры в монорепо на MVP; источник правды — контракт бэкенда (`Docs/concept.md` §12) |
| Пуши | **FCM** (`@react-native-firebase/messaging` + `notifee` для отображения) | Решение зафиксировано (§8) |
| Оффлайн-кэш | **MMKV + persister TanStack Query**, медиа — кэш на файловой системе | Оффлайн-режим нужен: сообщения и картинки сохраняются между запусками (§8) |
| OIDC-логин | **ROPC (direct grants) на клиенте `mobile` realm'а — основной флоу**; PKCE/Custom Tab — fallback | Полностью нативный вход/регистрация без браузера (§3.2); пользователи общие с вебом (один realm). ROPC допустим только для доверенного собственного приложения (как у веба, §5 концепции) |

Чего делать нельзя: Expo Go (не поддерживает FCM), встроенный webview для Keycloak-логина, P2P-обходы для realtime, redis-пакеты, ROPC для сторонних приложений.

## 3. Архитектура

### 3.1 Слои

```
UI (React Native экраны, Expo Router)
  │  только отображение и вызовы хуков/экшенов; бизнес-логики в компонентах нет
  ├── TanStack Query  ← REST-кэш: чаты, сообщения, файлы, профиль (+ персистентный оффлайн-кэш)
  ├── Zustand store   ← сессия (токены, /users/me) + realtime-состояние (presence, typing)
  └── Services        ← api-client, ws-client, media-cache, oidc-session, config (чистые TS-модули)
REST API (/api/v1), WebSocket (tickets), presigned Silo, FCM — существующий бэкенд
```

Правила зависимостей (сверху вниз, не наоборот):

- Экраны знают про хуки и сторы; сторы и services не знают про UI
- TanStack Query и Zustand не пересекаются: Query — серверные данные (истина на сервере), Zustand — только runtime-состояние (сессия, соединение, typing/presence)
- UI никогда не подписывается на WS напрямую — только через Query-кэш и store

Переиспользование с вебом: контракт API один (типы копируются в `mobile/src/api`, см. §2); компоненты и стили — раздельные (нативные стили Android). Трансформация ответов (нормализация сообщений, снапшоты пересылки, idempotency-обёртки) — по возможности одинаковые модули, но без общего пакета на MVP.

### 3.2 Аутентификация и регистрация (полностью нативные, без браузера)

Требование: **вход и регистрация — только внутри приложения**, без открытых веб-страниц. Пользователи веба и мобильного — общие автоматически: один Keycloak realm, одна БД.

- **Клиент `mobile` в realm-export**: отдельный client (public), `directAccessGrantsEnabled: true` (ROPC), audience mapper обязателен (правило AGENTS). Настройки не наследуются от клиента `frontend`.
- **Логин**: нативная форма (username + password) → ROPC-запрос к KC token endpoint → access/refresh токены. Пароль вводится только в нативной форме и не проходит через браузер/веб-страницу.
- **Регистрация**: нативная форма → `POST /auth/register` (инвайт-код или открытый режим `APP_OPEN_REGISTRATION`) → автовход через ROPC теми же учётными данными. KC-аккаунт создаёт бэкенд через Admin API (как у веба).
- **Fallback**: если ROPC у клиента `mobile` отключён/недоступен (ошибка token endpoint, обычно `invalid_grant`/403) → PKCE через Custom Tab (`vibechat://callback`). PKCE — запасной флоу, не основной.
- Дальше — как у веба: JWT валидируется бэкендом (JWKS, iss/aud/exp); клиент не парсит персональные данные из клеймов, всё берёт из `/users/me`
- Обновление токена — refresh flow; истечение JWT в живом WS — норма (§9 концепции)
- WS auth — тот же **одноразовый ticket** (`POST /ws/ticket`)

Жизненный цикл сессии:

| Состояние | Поведение |
|---|---|
| Холодный запуск | refresh-токен из защищённого хранилища → refresh → `/users/me` → WS-ticket → открыть WS → рендер из оффлайн-кэша → догоняние `updated_after` |
| Возврат в foreground | пинг WS; если оборван — реконнект + догоняние; refresh при близком exp |
| Background | WS закрывается (Android рвёт сокеты); уведомления — через FCM |
| refresh истёк / 401 | экран логина, очистка стора, кэша и ключей |

Токены — только в защищённом хранилище (react-native-keychain → Android Keystore); никогда в MMKV/AsyncStorage.

**Выход из аккаунта (logout)** — оркестрация в строгом порядке (services, не UI):

1. `DELETE /push/tokens/{token}` — отвязать устройство от пушей (пока есть валидный JWT)
2. KC logout (revoke refresh-токена; для ROPC-сессии — revoke endpoint Keycloak)
3. Закрыть WS, остановить реконнект-цикл
4. Очистить: Zustand-сторы, TanStack Query кэш + MMKV-persister, медиа-кэш, Keychain
5. Сброс navigation state → `/login`

**Смена аккаунта**: одна активная сессия на устройство. Выход (полный, по п.1–5) → вход другим пользователем. Два параллельных аккаунта не поддерживаются (post-MVP, при необходимости). Отказ в п.1–2 не блокирует очистку (п.4–5): если revoke не прошёл (сеть), локальная сессия всё равно уничтожается — серверный refresh-токен истечёт сам.

### 3.3 Realtime

- WebSocket + WS-ticket, как в вебе; client→server — только `typing`, мутации через REST
- Реконнект и догоняние пропущенного — курсоры `updated_after` (edit/delete) и пагинация по `message id` (UUIDv7)
- Presence и typing серверные события — без изменений; несколько соединений на пользователя допустимы

Архитектура ws-client:

- Один экземпляр на процесс (синглтон); автопереподключение с экспоненциальной задержкой + джиттер
- Входящие события — **одна точка диспетчеризации**: `message.*` → обновление ленты/инвалидация счётчиков в Query; `chat.*` → инвалидация списка чатов; presence/typing → Zustand
- Применение событий идемпотентно (upsert по `id`/`updated_at`) — дубли после реконнекта не ломают состояние
- Пагинация: лента `FlatList` с inverted-рендером, догрузка «вверх» по курсору `?before=` (UUIDv7), «вниз» — только через realtime/`updated_after`

### 3.4 Файлы и оффлайн-режим

- Без проксирования через бэкенд: **presigned PUT/GET напрямую в Silo**, как в вебе
- Внимание: `SILO_PUBLIC_URL` — scheme://host **без пути** (входят в подпись S3v4); этот host должен быть доступен с телефона. На стенде Silo отдаётся через системный nginx по `/vibe-files/` — путь в presigned URL сохраняется целиком (proxy_pass без слэша); браузерный CORS не применим (native-клиент)
- Требования к вложениям — те же, что у веба: real_mime определяет сервер (sniffing), `kind` вложения на клиенте — по `real_mime` от сервера; SVG — не image; `thumb_key`/`blurhash` приходят в `files`
- Метаданные видео извлекает клиент (ffmpeg на бэкенде нет); на Android — нативный MediaMetadataRetriever

Оффлайн-стратегия:

- **Сообщения/метаданные** — persister TanStack Query в MMKV: холодный старт без сети рендерит ленту из кэша, затем фоновое догоняние
- **Медиа** — кэш на файловой системе, key = `file_id` + `thumb_key`; скачанное не перекачивается; LRU-лимит ~500 МБ (настраивается)
- **Исходящие в оффлайне**: очередь неотправленных в MVP не строится (сервер — истина о времени сообщения); при ошибке сети — кнопка «повторить»; `client_ref`/`Idempotency-Key` защищают от дублей при ретраях
- **Blurhash** мгновенно, `thumb_key` — из кэша, оригинал по тапу

Загрузка вложений (мобильная специфика):

- Лимит бэкенда — `max_file_size_bytes` (100 МБ, конфигурируемый); клиент проверяет размер **до** presigned PUT — превентивный отказ с сообщением, без байт-подсчёта на сервере
- Прогресс-бар upload обязателен (мобильные сети медленные): `onProgress` из upload-запроса к Silo
- Отмена загрузки — кнопка в строке прогресса (abort запроса); файл остаётся `pending` и убирается cleanup'ом бэкенда через 24 ч

### 3.5 Push-уведомления (новое на бэкенде)

Мобильный клиент живёт с закрытым приложением — нужны пуши (контракт API — §3.8):

- **Транспорт**: Firebase Cloud Messaging (FCM)
- **Клиент**: получает FCM-токен, регистрирует его на бэкенде (`POST /push/tokens`), привязывает к текущему устройству/пользователю
- **Бэкенд**: новое —
  - таблица **device tokens** (PostgreSQL): `user_id`, `token`, `platform`, `last_seen_at`; при ротации токена FCM старый удаляется/обновляется
  - сервис отправки: при fanout сообщения в чат (Valkey Pub/Sub) — параллельно FCM для устройств пользователей без активного WS-соединения (presence-счётчик в Valkey уже есть)
  - payload — только идентификаторы (chat_id, message_id, count); контент сообщения клиент подтягивает сам через REST → не светим текст в FCM-шине; агрегация непрочитанных — §3.8
- **Показ**: `notifee` (локальное отображение из FCM-сообщения), deep link в чат (`vibechat://chat/{id}`)
- Правила ботов (`§10 концепции`) при пуши не нарушаются: пуш доставляет ту же логику событий `message.*`
- Триггер пуша — **только новые сообщения** (typing/presence/реакции не пушатся)

Дедупликация пуша и realtime:

- foreground + живой WS → FCM-сообщение молча идёт в Query (без уведомления), ленту обновляет realtime
- background/закрыто → notifee рисует уведомление
- тап по уведомлению → deep link в чат → догрузка контекста из кэша + REST

### 3.6 Навигация и deep links

- **Expo Router**: `/login` → `/(app)/chats` → `/(app)/chats/[id]`; guard на сессии — без refresh-токена редирект на `/login`
- Deep links: `vibechat://callback` (OIDC-редирект), `vibechat://chat/{chat_id}` (пуш); тап из холодного старта — сначала восстановление сессии, потом навигация в чат
- Android back — стандартное поведение Expo Router; overlay звонков поверх навигации — отдельный слой (следующие итерации)

### 3.7 Конфигурация и окружения

- Адреса (REST base, WS base, Silo public host, KC realm/urls) — только через env (`EXPO_PUBLIC_*`), как `VITE_*` у веба; без хардкода в рантайме
- Два профиля: dev (эмулятор, локальный бэкенд) и стенд `merch-vibe.ru` (`/chat` API/WS, `/vibe-files/` Silo, KC `:8444`); переключение через `.env` при сборке
- Самодиагностика на старте: доступность REST и host'а Silo — понятное сообщение вместо runtime-падений

### 3.8 Контракты API для мобильного (полный перечень)

Существующие эндпоинты (`/api/v1`, §12 концепции) используются как есть: auth, users, chats, messages (с `Idempotency-Key`/`client_ref`, `timezone`), reactions, files (presigned), ws/ticket. Специфика мобильного — только два новых бэкенд-эндпоинта:

**Пуш-токены** (новое, этап 6):

- `POST /push/tokens` — `{token, platform: "android"}`; привязка к текущему `sub` (из JWT); upsert по токену, обновление `last_seen_at`
- `DELETE /push/tokens/{token}` — отвязка (выход из аккаунта)
- Очистка: при ответе FCM `UNREGISTERED`/`INVALID_ARGUMENT` запись удаляется автоматически
- Гонка с реконнектом: пуш отправляется только если у пользователя **0 активных WS-соединений в момент fanout** (presence-счётчик); пользователь, переподключающийся через секунду, получит сообщение по догонянию — двойная доставка не считается ошибкой, клиент дедуплицирует (§3.5)
- **Агрегация**: если пользователь оффлайн и накопилось несколько непушёных сообщений — один пуш с количеством (payload: `chat_id`, `count`); контрольная точка — последнее непушёное `message_id` на устройство. Дедуп на клиенте по `message_id` в любом случае.

**Проверка минимальной версии** (новое, этап 8 — единственное исключение из «никаких мобильных эндпоинтов», оправдано APK-дистрибуцией без Play):

- `GET /app/version` (без аутентификации) — `{min_version, latest_version}`; константы в конфиге бэкенда
- Клиент при старте сравнивает свою версию с `min_version`: меньше — блокирующий экран «обновите приложение» с инструкцией установки нового APK (без маркета — прямая ссылка на раздачу/MDM)
- **Обновление в рантайме — отложено** (решение): баннер «доступна новая версия» при `version < latest_version` добавим после первого релиза, когда появится практика раздачи обновлений; сейчас — только жёсткая блокировка по `min_version`

Оба эндпоинта фиксируются в `Docs/concept.md` при реализации этапов 6/8.

### 3.9 Разрешения Android (targetSdk 35, целевая Android 13+)

| Разрешение | Когда запрашивается | Примечание |
|---|---|---|
| `POST_NOTIFICATIONS` | после первого успешного логина, объясняющий экран перед системным диалогом | На Android 13+ (API 33) — runtime-разрешение; без него пуши молча не приходят. Отказ — приложение работает без пушей, настройка в профиле повторно открывает запрос |
| Фото/файлы | **Photo Picker** (`ActivityResultContracts.PickVisualMedia`) — без разрешений вообще | Предпочтительно на API 33+; для произвольных файлов — `ACTION_OPEN_DOCUMENT` (SAF), тоже без permissions. Массовая загрузка из галереи — рассмотреть `READ_MEDIA_IMAGES` только если Picker не покроет (не в MVP) |
| Камера (съёмка вложения) | по кнопке «камера» в чате | `CAMERA` + FileProvider для передачи файла; не в первой итерации вложений, если не запроектировано |
| `INTERNET`, `ACCESS_NETWORK_STATE` | manifest, без запроса | базовые |

Явно фиксируется: `allowBackup=false` (чат-контент не должен попадать в adb backup / облачные бэкапы устройства).

### 3.10 UI-решения

- **Статусы отправки сообщения**: `sending` (часики) → `sent` (ответ 2xx REST, галочка) / `error` (кнопка «повторить»). Синхронизация через `client_ref`: REST-ответ и realtime-событие с одним `client_ref` — одно сообщение в ленте (upsert)
- **Список чатов**: сортировка по `last_message.id` (UUIDv7) — как у веба; непрочитанные — счётчик из `chat.*`/`message.*` событий (server-side прочитанность, не локальная эвристика)
- **Typing-индикатор**: событие WS → Zustand (`chat_id` → {user_id, timestamp}); UI показывает индикатор, пока событие свежее (< 5 с, таймер перерисовки), скрывает по истечении или при `message.*` от этого пользователя
- **Тема**: выбор в профиле — светлая / тёмная / системная (default). Реализация — три набора цветовых токенов (токен-подход с первого дня, не хардкод цветов в компонентах)
- **Строки**: словарь i18n с первого дня (`src/i18n/ru.ts`, `t('key')`) — хардкод строк в компонентах запрещён; выбор языка клиента — настройка в профиле (сейчас только `ru`, структура готова под новые локали). Словарь принят как решение, чтобы локализация добавлялась без трогания компонентов.
- **Обработка ошибок API — единая политика**: не блокирует UI; человекочитаемый текст из i18n-словаря (snackbar/toast внизу экрана, авто-скрытие ~4 с). Маппинг: сеть недоступна → «нет соединения»; 401 → разлогин (жизненный цикл §3.2); 403 → «нет доступа»; 409 идемпотентности → не показывается пользователю (сообщение уже существует, upsert молча); 422 → текст валидации от сервера; 5xx → «ошибка сервера, повторите позже». Отдельные UI-состояния — только у отправки сообщения (§ выше) и загрузки файла (§3.4).
- **Взаимодействие с сообщением** — как в вебе (§6 концепции): long-tap → контекстное меню (реакции: 5 фиксированных эмодзи; цитирование; пересылка; редактирование своего; удаление своего). Реакции — optimistic toggle. Системные сообщения (`type=system`) — без контекстного меню (нельзя цитировать/пересылать/реагировать). На mobile — компактный попап как hover-панель веба: ряд эмодзи сверху + строка действий «Ответить / Переслать / Удалить» (не полноэкранный список).
- **Пересылка (e2e-2026-11-25)**: `ForwardDialog` — Modal со списком чатов (кроме исходного, имена direct через useChatDetail как в списке), мультивыбор → `POST /messages/{id}/forward`; после успеха инвалидируется список чатов (пересланное поднимает `last_message_at`). Ленты целевых чатов не трогаем — догрузятся при открытии.
- **Профиль (e2e-2026-11-25)**: отдельный экран `(app)/profile.tsx` — username (read-only, из KC), display_name/first/last/email → `PATCH /users/me` (персональные данные — в системе, §5), time_display чипами + timezone при `fixed`; после сохранения синхронизируется `useSession.user.display_name` (шапка direct-чатов). Кнопка «Выйти» — на экране профиля (подтверждение через Alert), а не в шапке списка чатов — шапочная «Профиль» теперь только ведёт на экран.
- **Удалённые сообщения**: soft delete отображается как в вебе — плашка «сообщение удалено» (терминология концепции §6: «удалено у всех», per-user видимость); вложения при удалении скрываются; реакции на удалённом сообщении скрыты.
- **Первая страница истории**: 50 сообщений (лимит API по умолчанию, §12 концепции), догрузка вверх по скроллу.
- **Deep link в недоступный чат**: чат удалён (soft delete) или нет доступа → fallback на список чатов + snackbar «чат недоступен».

### 3.11 Observability и отладка

- **MVP (зафиксировано)**: debug-сборка — React Native DevTools + adb logcat + overlay с ошибками; release — локальное логирование ошибок в файл (диагностика через MDM/adb по запросу пользователя)
- **Кандидат post-MVP**: Sentry self-hosted (краши release-сборок); решение принять при появлении реальных пользователей на APK
- Логи не содержат персональных данных и текстов сообщений

### Ручной тест-план (регресс перед каждой release-сборкой)

1. Логин (ROPC) валидные/невалидные креды; регистрация инвайт-код; регистрация в открытом режиме
2. Logout → полный выход; вход вторым пользователем → данные первого не видны (пуш-токен отвязан, кэш чист)
3. Отправка текста; идемпотентность: ретрай при таймауте не создаёт дубль (`client_ref`)
4. Airplane mode: отправка → ошибка → «повторить» после включения сети; перезапуск в оффлайне → лента из кэша
5. Realtime: два устройства — доставка < 1 с, typing, presence, реакция у собеседника видна
6. Пагинация: скролл вверх загружает историю; `updated_after` восстанавливает ленту после реконнекта
7. Вложения: фото через Picker, прогресс, отмена, превью, blurhash; файл > лимита отклонён
8. Пуши: оффлайн-получатель получает пуш; foreground — без уведомления; тап из cold start → чат
9. Отказ `POST_NOTIFICATIONS` → приложение работает, пуши не приходят
10. Тема светлая/тёмная/системная применяется сразу; язык — из словаря (нет хардкод-строк)
11. Deep link из уведомления в удалённый чат → fallback список + snackbar
12. Удаление сообщения → плашка «удалено у всех» у обеих сторон; реакции на удалённом скрыты
13. `min_version`: старая версия → блокирующий экран

## 7. Скоуп MVP мобильного

**Входит (итерация 1):**
- Логин Keycloak (ROPC через нативную форму; PKCE — fallback) + регистрация (нативная форма, инвайт-код или открытый режим `APP_OPEN_REGISTRATION`) — §3.2
- Список чатов, лента сообщений, отправка текста
- Вложения: сетка картинок + список файлов, просмотр (upload-флоу Silo, превью, thumbnails/blurhash)
- Realtime (WS-соединение, typing, presence, догоняние)
- Push-уведомления (FCM) + deep link в чат; runtime-разрешение `POST_NOTIFICATIONS` (§3.9)
- Тема: светлая/тёмная/системная (§3.10); выбор языка клиента — настройка профиля, словарь i18n
- Реакции, цитирование, пересылка — просмотр
- Профиль (просмотр/редактирование `PATCH /users/me`)
- Обязательные клиентские требования из концепции:
  - `Idempotency-Key`/`client_ref` при отправке сообщений (мобильная сеть нестабильна — ретраи без дублей критичны)
  - передача `messages.timezone` (эффективный пояс отправителя, IANA) при отправке; отображение времени — по `users.time_display`

**Следующие итерации:**
- Звонки (аудио/видео через LiveKit; на бэкенде реализованы — этапы A/B/C §17, сигналинг `call.*` через общий WS; медиа — напрямую в LiveKit по room-токену, как у веба; room-JWT TTL ~10 мин — единственный случай, когда бэкенд выдаёт токен)
- Мини-доработки: поиск, management-функции чатов (администрирование участников)

**Не входит:** mini-apps UI (§11 — каркас без UI); боты (серверная подсистема, в UI отображаются как участники чата — отдельной работы нет).

## 9. Решённые вопросы

- **Пуши — FCM, решение зафиксировано.** Альтернатива (UnifiedPush/own push-шлюз) рассматривается только если корпоративные ограничения на Google-сервисы ужесточатся.
- **Оффлайн-режим нужен**: загруженные данные (сообщения, картинки и т.п.) должны сохраняться между запусками. Реализация — персистентный кэш (MMKV для мелких данных + кэш медиа на файловой системе поверх presigned GET); TanStack Query с persister даёт базу. Кэш сообщений — этап 3, медиа-кэш — этап 5 (§8).
- **iOS не планируется** на MVP; выбор Expo сохраняет возможность позже без смены стека.
- **Версионирование API** — по мере необходимости: `/api/v1` уже есть, обратная совместимость соблюдается в рамках обычных изменений. Специальных механизмов (слотирование версий, freeze) на MVP не вводим.
- **WS-реконнект не плодит соединения (этап 4, e2e)**: сокет присваивается в модульной переменной ДО навешивания хендлеров; `onclose` проверяет `socket !== ws` и игнорирует закрытие заменённого сокета — иначе каждый реконнект оставлял висящий старый сокет, сервер плодил connection'ы (видно в uvicorn-логе: череда `POST /ws/ticket` + `WebSocket ... [accepted]` без закрытий).
- **WS `message.*` приходит обёрнутым (этап 4, e2e)**: бэкенд публикует payload как `{message: <MessageOut>}` (§9 концепции), клиентский `asMessage` разворачивает `data.message ?? data` — без этого все live-события молча отбрасывались (доставка работала только через refetch/catchUp).
- **Presence-heartbeat на бэкенде (этап 4)**: `presence_touch` объявлен, но нигде не вызывался — ключ протухал через 60 с при живом WS; в `ws_endpoint` добавлена задача `_presence_heartbeat` (touch каждые 30 c, включена в `asyncio.wait` + cancel в finally).
- **Optimistic-отправка мержится по `client_ref` (этап 5, e2e)**: локальное сообщение обязано нести `client_ref` = Idempotency-Key, и ключ генерируется один раз вызывающим (передаётся через variables мутации) — `onMutate` и `mutationFn` используют один ключ; иначе серверный ответ/WS-событие не находят локальную запись и статус навсегда «Отправка…».
- **`asset.fileSize` из Photo Picker врёт (этап 5, e2e)**: `content://` → blob другого размера (у тестового фото подписали 13805, факт — 11821) → S3-подпись требует точного Content-Length → 403 SignatureDoesNotMatch. Размер для upload-url берётся **только** из `blob.size` (fetch до upload-url). Content-Type в presigned PUT не подписывается (XHR мог слать другой CT; реальный mime определяет sniffing при complete) — `presign_put(storage_key, size, ttl)`.
- **Лимит 100 МБ — двухступенчатый (этап 5)**: pre-check по `asset.fileSize` ДО fetch (fetch 108 МБ `content://` в RN падает «Network request failed» — Blob memory-backed), точная проверка по `blob.size` после fetch. Без pre-check большой файл падает с неинформативной сетевой ошибкой вместо FileTooLargeError+Alert.
- **Эмодзи-реакции — имена, не символы (e2e)**: API хранит имена (`thumbs_up`/`heart`/`laugh`/`fire`/`check`, сверка с `ALLOWED_EMOJI` на бэкенде); веб так и отправляет. Мобильный клиент изначально отправлял Unicode-символы («👍») → 422. Контракт: клиент отправляет имя, чипы рендерят `EMOJI_CHAR[name] ?? name`.
- **Лайтбокс — только Modal (e2e)**: полноэкранный просмотр картинок как plain absolute View внутри Stack-экрана рендерится поверх ленты, но тач по фону (закрытие) не получает — Pressable внутри «пустого» оверлея не срабатывает. Решение — `<Modal transparent>` (как контекстное меню чата): отдельное окно, тачи гарантированы; заодно «×»-кнопка не нужна — закрытие тапом по фону или back (onRequestClose).
- **Logout обязан чистить MMKV-кэш (e2e)**: `clearCacheStorage()` существовал, но не вызывался — оффлайн-кэш чатов/сообщений переживал выход, следующий пользователь на устройстве получал 403 при догонянии чужих чатов (и видел хвосты в оффлайне). Вызов добавлен в `logoutLocal` (§3.2).
