# Мобильное приложение (Android)

> Документ описывает мобильный клиент vibe-chat для Android. Продуктовая и архитектурная правда — в `Docs/concept.md`; этот документ конкретизирует её для мобильной платформы. При противоречии приоритет у концепции.

## 1. Обзор

Мобильный клиент — **не отдельный продукт, а вторая площадка того же мессенджера**: тот же бэкенд, тот же REST/WS API (`/api/v1`), тот же Keycloak и тот же Silo. Никаких отдельных мобильных эндпоинтов на MVP — только то, что уже существует, плюс транспорт push-уведомлений (§3.5).

- Целевая ОС: **Android 13+ (API 33)**, `targetSdk` — актуальный стабильный (35)
- Дистрибуция на MVP: **APK напрямую** (sideload / MDM), Google Play не используется → требования к релизу упрощены (нет Data Safety, privacy policy Play Console; подпись — self-signed)
- Мобильный клиент ходит на тот же стенд (`merch-vibe.ru`): API/WS через `/chat`, вложения через `/vibe-files/`, KC через `:8444` — конфигурируется на этапе каркаса (как `VITE_*` у веба)
- Язык приложения и документации — русский

## 2. Стек

Зафиксировано:

| Компонент | Решение | Обоснование |
|---|---|---|
| Фреймворк | **React Native + Expo** (development build, не Expo Go) | Пуши и нативные модули требуют dev build; Expo Go не подходит |
| Язык | TypeScript | Единый со `frontend/` |
| UI | React Native компоненты (нативные стили Android) | Tailwind/shadcn — web-only, на мобильном не переиспользуются |
| Data layer | **TanStack Query (REST-кэш) + Zustand (WS-состояние)** | Как в `frontend/` — одинаковые паттерны обеих площадок |
| Типы API | Копия контракта в `mobile/src/api` на старте; при первом расхождении — вынести общий workspace-пакет `packages/api-types` | Минимум инфраструктуры в монорепо на MVP; источник правды — контракт бэкенда (`Docs/concept.md` §12) |
| Пуши | **FCM** (`@react-native-firebase/messaging` + `notifee` для отображения) | Решение зафиксировано (§8) |
| Оффлайн-кэш | **MMKV + persister TanStack Query**, медиа — кэш на файловой системе | Оффлайн-режим нужен: сообщения и картинки сохраняются между запусками (§8) |
| OIDC-логин | **ROPC (direct grants) на клиенте `mobile` realm'а — основной флоу**; PKCE/Custom Tab — fallback | Полностью нативный вход/регистрация без браузера (§3.2); пользователи общие с вебом (один realm). ROPC допустим только для доверенного собственного приложения (как у веба, §5 концепции) |

Чего делать нельзя: Expo Go (не поддерживает FCM), встроенный webview для Keycloak-логина, P2P-обходы для realtime, redis-пакеты, ROPC для сторонних приложений.

## 3. Архитектура

### 3.1 Слои

```
UI (React Native экраны, Expo Router)
  │  только отображение и вызовы хуков/экшенов; бизнес-логики в компонентах нет
  ├── TanStack Query  ← REST-кэш: чаты, сообщения, файлы, профиль (+ персистентный оффлайн-кэш)
  ├── Zustand store   ← сессия (токены, /users/me) + realtime-состояние (presence, typing)
  └── Services        ← api-client, ws-client, media-cache, oidc-session, config (чистые TS-модули)
REST API (/api/v1), WebSocket (tickets), presigned Silo, FCM — существующий бэкенд
```

Правила зависимостей (сверху вниз, не наоборот):

- Экраны знают про хуки и сторы; сторы и services не знают про UI
- TanStack Query и Zustand не пересекаются: Query — серверные данные (истина на сервере), Zustand — только runtime-состояние (сессия, соединение, typing/presence)
- UI никогда не подписывается на WS напрямую — только через Query-кэш и store

Переиспользование с вебом: контракт API один (типы копируются в `mobile/src/api`, см. §2); компоненты и стили — раздельные (нативные стили Android). Трансформация ответов (нормализация сообщений, снапшоты пересылки, idempotency-обёртки) — по возможности одинаковые модули, но без общего пакета на MVP.

### 3.2 Аутентификация и регистрация (полностью нативные, без браузера)

Требование: **вход и регистрация — только внутри приложения**, без открытых веб-страниц. Пользователи веба и мобильного — общие автоматически: один Keycloak realm, одна БД.

- **Клиент `mobile` в realm-export**: отдельный client (public), `directAccessGrantsEnabled: true` (ROPC), audience mapper обязателен (правило AGENTS). Настройки не наследуются от клиента `frontend`.
- **Логин**: нативная форма (username + password) → ROPC-запрос к KC token endpoint → access/refresh токены. Пароль вводится только в нативной форме и не проходит через браузер/веб-страницу.
- **Регистрация**: нативная форма → `POST /auth/register` (инвайт-код или открытый режим `APP_OPEN_REGISTRATION`) → автовход через ROPC теми же учётными данными. KC-аккаунт создаёт бэкенд через Admin API (как у веба).
- **Fallback**: если ROPC у клиента `mobile` отключён/недоступен (ошибка token endpoint, обычно `invalid_grant`/403) → PKCE через Custom Tab (`vibechat://callback`). PKCE — запасной флоу, не основной.
- Дальше — как у веба: JWT валидируется бэкендом (JWKS, iss/aud/exp); клиент не парсит персональные данные из клеймов, всё берёт из `/users/me`
- Обновление токена — refresh flow; истечение JWT в живом WS — норма (§9 концепции)
- WS auth — тот же **одноразовый ticket** (`POST /ws/ticket`)

Жизненный цикл сессии:

| Состояние | Поведение |
|---|---|
| Холодный запуск | refresh-токен из защищённого хранилища → refresh → `/users/me` → WS-ticket → открыть WS → рендер из оффлайн-кэша → догоняние `updated_after` |
| Возврат в foreground | пинг WS; если оборван — реконнект + догоняние; refresh при близком exp |
| Background | WS закрывается (Android рвёт сокеты); уведомления — через FCM |
| refresh истёк / 401 | экран логина, очистка стора, кэша и ключей |

Токены — только в защищённом хранилище (react-native-keychain → Android Keystore); никогда в MMKV/AsyncStorage.

**Выход из аккаунта (logout)** — оркестрация в строгом порядке (services, не UI):

1. `DELETE /push/tokens/{token}` — отвязать устройство от пушей (пока есть валидный JWT)
2. KC logout (revoke refresh-токена; для ROPC-сессии — revoke endpoint Keycloak)
3. Закрыть WS, остановить реконнект-цикл
4. Очистить: Zustand-сторы, TanStack Query кэш + MMKV-persister, медиа-кэш, Keychain
5. Сброс navigation state → `/login`

**Смена аккаунта**: одна активная сессия на устройство. Выход (полный, по п.1–5) → вход другим пользователем. Два параллельных аккаунта не поддерживаются (post-MVP, при необходимости). Отказ в п.1–2 не блокирует очистку (п.4–5): если revoke не прошёл (сеть), локальная сессия всё равно уничтожается — серверный refresh-токен истечёт сам.

### 3.3 Realtime

- WebSocket + WS-ticket, как в вебе; client→server — только `typing`, мутации через REST
- Реконнект и догоняние пропущенного — курсоры `updated_after` (edit/delete) и пагинация по `message id` (UUIDv7)
- Presence и typing серверные события — без изменений; несколько соединений на пользователя допустимы

Архитектура ws-client:

- Один экземпляр на процесс (синглтон); автопереподключение с экспоненциальной задержкой + джиттер
- Входящие события — **одна точка диспетчеризации**: `message.*` → обновление ленты/инвалидация счётчиков в Query; `chat.*` → инвалидация списка чатов; presence/typing → Zustand
- Применение событий идемпотентно (upsert по `id`/`updated_at`) — дубли после реконнекта не ломают состояние
- Пагинация: лента `FlatList` с inverted-рендером, догрузка «вверх» по курсору `?before=` (UUIDv7), «вниз» — только через realtime/`updated_after`

### 3.4 Файлы и оффлайн-режим

- Без проксирования через бэкенд: **presigned PUT/GET напрямую в Silo**, как в вебе
- Внимание: `SILO_PUBLIC_URL` — scheme://host **без пути** (входят в подпись S3v4); этот host должен быть доступен с телефона. На стенде Silo отдаётся через системный nginx по `/vibe-files/` — путь в presigned URL сохраняется целиком (proxy_pass без слэша); браузерный CORS не применим (native-клиент)
- Требования к вложениям — те же, что у веба: real_mime определяет сервер (sniffing), `kind` вложения на клиенте — по `real_mime` от сервера; SVG — не image; `thumb_key`/`blurhash` приходят в `files`
- Метаданные видео извлекает клиент (ffmpeg на бэкенде нет); на Android — нативный MediaMetadataRetriever

Оффлайн-стратегия:

- **Сообщения/метаданные** — persister TanStack Query в MMKV: холодный старт без сети рендерит ленту из кэша, затем фоновое догоняние
- **Медиа** — кэш на файловой системе, key = `file_id` + `thumb_key`; скачанное не перекачивается; LRU-лимит ~500 МБ (настраивается)
- **Исходящие в оффлайне**: очередь неотправленных в MVP не строится (сервер — истина о времени сообщения); при ошибке сети — кнопка «повторить»; `client_ref`/`Idempotency-Key` защищают от дублей при ретраях
- **Blurhash** мгновенно, `thumb_key` — из кэша, оригинал по тапу

Загрузка вложений (мобильная специфика):

- Лимит бэкенда — `max_file_size_bytes` (100 МБ, конфигурируемый); клиент проверяет размер **до** presigned PUT — превентивный отказ с сообщением, без байт-подсчёта на сервере
- Прогресс-бар upload обязателен (мобильные сети медленные): `onProgress` из upload-запроса к Silo
- Отмена загрузки — кнопка в строке прогресса (abort запроса); файл остаётся `pending` и убирается cleanup'ом бэкенда через 24 ч

### 3.5 Push-уведомления (новое на бэкенде)

Мобильный клиент живёт с закрытым приложением — нужны пуши (контракт API — §3.8):

- **Транспорт**: Firebase Cloud Messaging (FCM)
- **Клиент**: получает FCM-токен, регистрирует его на бэкенде (`POST /push/tokens`), привязывает к текущему устройству/пользователю
- **Бэкенд**: новое —
  - таблица **device tokens** (PostgreSQL): `user_id`, `token`, `platform`, `last_seen_at`; при ротации токена FCM старый удаляется/обновляется
  - сервис отправки: при fanout сообщения в чат (Valkey Pub/Sub) — параллельно FCM для устройств пользователей без активного WS-соединения (presence-счётчик в Valkey уже есть)
  - payload — содержит контент (решение 2026-11-25, вместо прежних «только идентификаторы»: headless JS не имеет доступа к кэшу/REST — показать «от кого и что» иначе нельзя): `chat_id`, `message_id`, `count`, `title` (название чата: direct — имя собеседника, group — title), `body` (готовая строка: текст сообщения / «отправитель: текст» в группе / «N новых сообщений» при склейке), `lines` (JSON — до 5 последних непушенных сообщений «отправитель: текст», для InboxStyle при count>1). Текст виден в FCM-шине — осознанный компромисс (у Web Push для веба payload шифруется end-to-end); агрегация непрочитанных — §3.8
- **Показ**: `notifee` (локальное отображение из FCM-сообщения), deep link в чат (`vibechat://chat/{id}`)
- Правила ботов (`§10 концепции`) при пуши не нарушаются: пуш доставляет ту же логику событий `message.*`
- Триггер пуша — **только новые сообщения** (typing/presence/реакции не пушатся)

Дедупликация пуша и realtime:

- foreground + живой WS → FCM-сообщение молча идёт в Query (без уведомления), ленту обновляет realtime
- background/закрыто → notifee рисует уведомление
- тап по уведомлению → deep link в чат → догрузка контекста из кэша + REST

### 3.6 Навигация и deep links

- **Expo Router**: `/login` → `/(app)/chats` → `/(app)/chats/[id]`; guard на сессии — без refresh-токена редирект на `/login`
- Deep links: `vibechat://callback` (OIDC-редирект), `vibechat://chat/{chat_id}` (пуш); тап из холодного старта — сначала восстановление сессии, потом навигация в чат
- Android back — стандартное поведение Expo Router; overlay звонков поверх навигации — отдельный слой (следующие итерации)

### 3.7 Конфигурация и окружения

- Адреса (REST base, WS base, Silo public host, KC realm/urls) — только через env (`EXPO_PUBLIC_*`), как `VITE_*` у веба; без хардкода в рантайме
- Два профиля: dev (эмулятор, локальный бэкенд) и стенд `merch-vibe.ru` (`/chat` API/WS, `/vibe-files/` Silo, KC `:8444`); переключение через `.env` при сборке
- Самодиагностика на старте: доступность REST и host'а Silo — понятное сообщение вместо runtime-падений

### 3.13 Server selection (self-host; Docs/concept.md §19) — РЕАЛИЗОВАНО 2026-11-26

- **Порядок запуска:** (1) профиль сервера не задан → экран «Подключение» (`app/connect.tsx`): адрес + опциональное кодовое слово → `GET /server/info` (+ `X-Vibe-Join`) → сохранение профиля; (2) version-gate (§3.8) по `min_version` из профиля/`/app/version`; (3) логин/регистрация. Gate/banner теперь живут ПОСЛЕ выбора сервера.
- **Решения:** https-only в релизе (debug разрешает `http://10.0.2.2`/`localhost` — dev-тестирование); дефолтного сервера в сборке нет (поле пустое); кодовое слово opt-in (пусто на сервере = не запрашивается); смена сервера = подтверждение + logout + чистка MMKV-кэша и медиа-кэша.
- **config.ts → динамический (реализовано):** статические `EXPO_PUBLIC_API_BASE/WS_BASE/KC_*` удалены; всё читается из профиля сервера (`kc_url`, `realm` из `/server/info`; client id `mobile` — константа продукта; base-ы выводятся из адреса: `{base}/api/v1`, WS `{base}/api/v1/ws` — схема ws/wss по протоколу). Адрес может быть origin или префиксом точки монтирования бэкенда (стенд: `https://merch-vibe.ru/chat`); каноническая схема — origin (§19.2 концепции). Silo-адрес клиенту не нужен: URL вложений приходят в сериализации от бэкенда.
- **Профиль** — `{base_url, join_code, name, kc_url, realm, push, min/latest_version, app_download_url}` в MMKV (`vibe-server`, отдельный инстанс от кэша ленты); реактивный доступ — zustand `useServerProfile` (layout перерисовывается при подключении/смене). `X-Vibe-Join` добавляется api-client'ом ко всем запросам к своему серверу, если код задан (сервер требует его только на неаутентифицированных эндпоинтах; слать на все — безвредно).
- **Диагностика (§3.7) упрощена:** осталась только проверка REST (`{apiBase}/openapi.json`); silo-probe удалён (адреса вложений клиенту не нужны).
- **e2e 2026-11-26 (эмулятор):** cold start → connect → `http://10.0.2.2:8002` → логин admin → чаты/отправка/realtime работают; профиль → «Сменить сервер» → подтверждение → logout+чистка → connect; кодовое слово: без кода — ошибка «требует кодовое слово» (403), с кодом — подключение. Грабли: (1) ADBKeyboard надо выставлять (`ime set com.android.adbkeyboard/.AdbIME`) после пересоздания активити, иначе `input text` молча не вводит; (2) при смене сервера НЕ делать `router.replace` после снятия профиля — Stack размонтируется целиком, replace без живого навигатора даёт «action REPLACE not handled» (LogBox); навигацию не трогаем вообще.
- **Пуши (§3.5 + §19.6 концепции) — серверная возможность, не клиентская (реализовано, без живого e2e чужого проекта — см. спайк):** универсальный APK работает с любым сервером; наличие пушей определяет `push.driver` из `/server/info`. `off` → FCM не регистрируется и обработчики не ставятся (остальное работает); `fcm` без `push.firebase` → **пуши отключены** (токен официального проекта серверу, не назвавшему свой проект, не выдаётся — fallback на дефолт убран); чужой `project_id` → рантайм `initializeApp` (secondary app `vibe-server`, `initializeApp` в RN Firebase возвращает промис) + `getMessaging(app)`; совпадает с зашитым — дефолт как раньше; нерабочий конфиг сервера → пуши отключены, НИКОГДА fallback на дефолт. Все хендлеры (onMessage/background/tokenRefresh) ставятся на активный инстанс. Токен — адрес, не креды: слать может только держатель SA-ключа проекта (§19.6). Смена сервера → `resetSecondaryFirebaseApp()` (deleteApp) после logout.
- **LiveKit**: не меняется — `ws_url` приходит в room-токене от бэкенда (§3.12), клиент никогда его не вычисляет; `EXPO_PUBLIC_LIVEKIT_URL` остался как dev-override (единственный оставшийся `EXPO_PUBLIC_*`).

### 3.8 Контракты API для мобильного (полный перечень)

Существующие эндпоинты (`/api/v1`, §12 концепции) используются как есть: auth, users, chats, messages (с `Idempotency-Key`/`client_ref`, `timezone`), reactions, files (presigned), ws/ticket. Специфика мобильного — только два новых бэкенд-эндпоинта:

**Пуш-токены** (новое, этап 6):

- `POST /push/tokens` — `{token, platform: "android"}`; привязка к текущему `sub` (из JWT); upsert по токену, обновление `last_seen_at`
- `DELETE /push/tokens/{token}` — отвязка (выход из аккаунта)
- Очистка: при ответе FCM `UNREGISTERED`/`INVALID_ARGUMENT` запись удаляется автоматически
- Гонка с реконнектом: пуш отправляется только если у пользователя **0 активных WS-соединений в момент fanout** (presence-счётчик); пользователь, переподключающийся через секунду, получит сообщение по догонянию — двойная доставка не считается ошибкой, клиент дедуплицирует (§3.5)
- **Агрегация**: если пользователь оффлайн и накопилось несколько непушёных сообщений — один пуш с количеством (payload: `chat_id`, `count`); контрольная точка — последнее непушёное `message_id` на устройство. Дедуп на клиенте по `message_id` в любом случае.

**Проверка минимальной версии** (новое, этап 8 — единственное исключение из «никаких мобильных эндпоинтов», оправдано APK-дистрибуцией без Play):

- `GET /app/version` (без аутентификации) — `{min_version, latest_version}`; константы в конфиге бэкенда
- Клиент при старте сравнивает свою версию с `min_version`: меньше — блокирующий экран «обновите приложение» с инструкцией установки нового APK (без маркета — прямая ссылка на раздачу/MDM)
- **Баннер «доступна новая версия» — реализован (2026-11-26)**: при `version < latest_version` — неблокирующая полоса над контентом («Доступна новая версия (X.Y.Z)» + ✕-скрытие; тап — ссылка из `EXPO_PUBLIC_APP_DOWNLOAD_URL`, если задана). Live рядом с блокирующим гейтом в `app/_layout.tsx`; скрытие живёт в сессии (после рестарта — снова). Грабля: контент баннера обязан учитывать safe-area inset статус-бара (`useSafeAreaInsets`) — на вырезных устройствах ✕ под статус-баром (инсет 136 px на эмуляторе) недостижим для тапов.

Оба эндпоинта фиксируются в `Docs/concept.md` при реализации этапов 6/8.

### 3.9 Разрешения Android (targetSdk 35, целевая Android 13+)

| Разрешение | Когда запрашивается | Примечание |
|---|---|---|
| `POST_NOTIFICATIONS` | после первого успешного логина, объясняющий экран перед системным диалогом | На Android 13+ (API 33) — runtime-разрешение; без него пуши молча не приходят. Отказ — приложение работает без пушей, настройка в профиле повторно открывает запрос |
| Фото/файлы | **Photo Picker** (`ActivityResultContracts.PickVisualMedia`) — без разрешений вообще | Предпочтительно на API 33+; для произвольных файлов — `ACTION_OPEN_DOCUMENT` (SAF), тоже без permissions. Массовая загрузка из галереи — рассмотреть `READ_MEDIA_IMAGES` только если Picker не покроет (не в MVP) |
| Камера (съёмка вложения) | по кнопке «камера» в чате | `CAMERA` + FileProvider для передачи файла; не в первой итерации вложений, если не запроектировано |
| `INTERNET`, `ACCESS_NETWORK_STATE` | manifest, без запроса | базовые |

Явно фиксируется: `allowBackup=false` (чат-контент не должен попадать в adb backup / облачные бэкапы устройства).

### 3.10 UI-решения

- **Статусы отправки сообщения**: `sending` (часики) → `sent` (ответ 2xx REST, галочка) / `error` (кнопка «повторить»). Синхронизация через `client_ref`: REST-ответ и realtime-событие с одним `client_ref` — одно сообщение в ленте (upsert)
- **Список чатов**: сортировка по `last_message.id` (UUIDv7) — как у веба; непрочитанные — счётчик из `chat.*`/`message.*` событий (server-side прочитанность, не локальная эвристика)
- **Typing-индикатор**: событие WS → Zustand (`chat_id` → {user_id, timestamp}); UI показывает индикатор, пока событие свежее (< 5 с, таймер перерисовки), скрывает по истечении или при `message.*` от этого пользователя
- **Тема**: выбор в профиле — светлая / тёмная / системная (default). Реализация — три набора цветовых токенов (токен-подход с первого дня, не хардкод цветов в компонентах)
- **Строки**: словарь i18n с первого дня (`src/i18n/ru.ts`, `t('key')`) — хардкод строк в компонентах запрещён; выбор языка клиента — настройка в профиле (сейчас только `ru`, структура готова под новые локали). Словарь принят как решение, чтобы локализация добавлялась без трогания компонентов.
- **Обработка ошибок API — единая политика**: не блокирует UI; человекочитаемый текст из i18n-словаря (snackbar/toast внизу экрана, авто-скрытие ~4 с). Маппинг: сеть недоступна → «нет соединения»; 401 → разлогин (жизненный цикл §3.2); 403 → «нет доступа»; 409 идемпотентности → не показывается пользователю (сообщение уже существует, upsert молча); 422 → текст валидации от сервера; 5xx → «ошибка сервера, повторите позже». Отдельные UI-состояния — только у отправки сообщения (§ выше) и загрузки файла (§3.4).
- **Взаимодействие с сообщением** — как в вебе (§6 концепции): long-tap → контекстное меню (реакции: 5 фиксированных эмодзи; цитирование; пересылка; редактирование своего; удаление своего). Реакции — optimistic toggle. Системные сообщения (`type=system`) — без контекстного меню (нельзя цитировать/пересылать/реагировать). На mobile — компактный попап как hover-панель веба: ряд эмодзи сверху + строка действий «Ответить / Переслать / Удалить» (не полноэкранный список).
- **Пересылка (e2e-2026-11-25)**: `ForwardDialog` — Modal со списком чатов (кроме исходного, имена direct через useChatDetail как в списке), мультивыбор → `POST /messages/{id}/forward`; после успеха инвалидируется список чатов (пересланное поднимает `last_message_at`). Ленты целевых чатов не трогаем — догрузятся при открытии.
- **Профиль (e2e-2026-11-25)**: отдельный экран `(app)/profile.tsx` — username (read-only, из KC), display_name/first/last/email → `PATCH /users/me` (персональные данные — в системе, §5), time_display чипами + timezone при `fixed`; после сохранения синхронизируется `useSession.user.display_name` (шапка direct-чатов). Кнопка «Выйти» — на экране профиля (подтверждение через Alert), а не в шапке списка чатов — шапочная «Профиль» теперь только ведёт на экран.
- **Удалённые сообщения**: soft delete отображается как в вебе — плашка «сообщение удалено» (терминология концепции §6: «удалено у всех», per-user видимость); вложения при удалении скрываются; реакции на удалённом сообщении скрыты.
- **Первая страница истории**: 50 сообщений (лимит API по умолчанию, §12 концепции), догрузка вверх по скроллу.
- **Deep link в недоступный чат**: чат удалён (soft delete) или нет доступа → fallback на список чатов + snackbar «чат недоступен».

### 3.11 Observability и отладка

- **MVP (зафиксировано)**: debug-сборка — React Native DevTools + adb logcat + overlay с ошибками; release — локальное логирование ошибок в файл (диагностика через MDM/adb по запросу пользователя)
- **Кандидат post-MVP**: Sentry self-hosted (краши release-сборок); решение принять при появлении реальных пользователей на APK
- Логи не содержат персональных данных и текстов сообщений

### 3.12 Звонки (этапы 9–10; бэкенд и веб — §17 концепции, реализованы)

Сигналинг и медиа — ровно как у веба (§17): REST-мутации `/calls*`, WS-события `call.*` через общий realtime-диспетчер (§3.3), медиа — прямое подключение к LiveKit по room-токену из `POST /calls/{id}/token`. Бэкенду ничего не нужно — вся работа на клиенте.

**SDK и нативная интеграция**

- Пакеты: `livekit-client` + `@livekit/react-native` + `@livekit/react-native-webrtc` (пример SDK собран с `newArchEnabled=true` — совместимо с нашей Fabric-сборкой)
- `index.js`: `registerGlobals()` до AppRegistry (там же, где headless push)
- `MainApplication.kt`: `LiveKitReactNative.setup(this, AudioType.CommunicationAudioType())` до RN-инициализации (audio routing: earpiece/динамик, эхоподавление)
- Разрешения в манифесте: `RECORD_AUDIO` (уже есть), добавляются `CAMERA`, `MODIFY_AUDIO_SETTINGS`, `BLUETOOTH_CONNECT`; runtime-запрос — `PermissionsAndroid` перед start/accept/join (отказ микрофона → error в сторе, камера при видео → fallback «только звук»)
- `gradle.properties`: `android.enableDexingArtifactTransform.desugaring=false` (фикс WebRTC-рантайма из AndroidInstallation.md)
- В `app.json` добавлены плагины `@livekit/react-native-expo-plugin` + `@config-plugins/react-native-webrtc` — нужны только будущим `expo prebuild`; текущий bare-`android/` правится руками

**LiveKit URL и dev-топология**

- `token.ws_url` возвращает бэкенд (`APP_LIVEKIT_WS_URL`); в dev это `ws://localhost:7880`, что из эмулятора не резолвится → optional override `EXPO_PUBLIC_LIVEKIT_URL` в конфиге (dev: `ws://10.0.2.2:7880`; на стенде не задан — `wss://merch-vibe.ru/chat/livekit` корректен как есть)
- ICE-кандидаты LiveKit анонсирует от `--node-ip`; dev-дефолт `127.0.0.1` обслуживает браузер на хосте, но из эмулятора `127.0.0.1` — сам эмулятор → медиа не пойдёт. Для тест-сессий задаётся в `deploy/.env` (`LIVEKIT_NODE_IP=192.168.1.64` — LAN-адрес хоста; **переменные окружения из WSL-шелла в интерполяцию docker.exe compose НЕ попадают — только deploy/.env**), после тестов вернуть `127.0.0.1`. Для двух-устройственных звонков (эмулятор + телефон) media-путь эмулятора идёт через dev-coturn (см. §9); телефон и браузер ходят напрямую на node-ip. Подробности — §9
- `rtc.turn_servers`/`stun_servers` в `deploy/livekit/livekit.yaml` — dev-coturn (сервис `coturn` в docker-compose.yml, порт 3478/udp+tcp, relay 49160–49200/udp): LiveKit анонсирует его клиентам через сигналинг (проверено raw-WS JoinResponse), изменений на клиентах не нужно. Адреса в `turn_servers`/`external-ip` — специфичны для машины (WSL eth0 + LAN IP) и задаются в `deploy/.env` (`TURN_EXTERNAL_IP`)/yaml — при переносе обновить.
- `AudioSession.startAudioSession()` перед `room.connect`, `stopAudioSession()` при разрыве; звонок в фоне не держится (foreground service — перспектива, не MVP)
- **Микрофон эмулятора по умолчанию — тишина (e2e, 2026-11-25)**: двустороннее аудио в эмуляторе работает только после «Extended Controls → Microphone → Virtual microphone uses host input» (+ разрешение микрофона для классических приложений в Windows-приватности). До этого трек с телефона публикуется нормально (LiveKit видит unmuted audio track), но несёт тишину: «веб → телефон» слышно, «телефон → веб» — нет

**Состояние и UI**

- Стор — порт вебового `frontend/src/realtime/calls.ts` в `mobile/src/stores/calls.ts` (Zustand вне TanStack Query): `current`/`room`/`media`/`remoteIds`/`muted`/`camOn`, методы start/accept/reject/cancel/join/leave/toggle*; WS-диспатч `call.*` — в `realtime-sync.ts` (case → стор)
- Ринг — звуковой файл + вибрация (не WebAudio как в вебе): `expo-audio`, луп `assets/sounds/ring.wav` (2-тональный, генерируется скриптом)
- UI — `src/components/call-overlay.tsx` у корня `(app)/_layout` (звонок не рвётся при навигации, как в вебе): ринг-карточка direct (Ответить/Отклонить; у инициатора — Отменить), баннер чужого group-звонка с «Присоединиться», панель активного аудио (таймер от `started_at`, mute, hang-up, состав из `participant_ids` через кэш чата), полноэкранный видео-оверлей — этап 10
- **Оверлей в `<Modal>` (e2e)**: sibling-View над native-stack (react-native-screens) не гарантирует z-порядок — панель активного звонка получала нативный узел с корректными bounds (dumpsys), но рисовалась ЗА содержимым экрана (пиксели пустые, a11y-узлов нет), при этом ринг-карточка с elevation 12 была видна. Решение — всё содержимое оверлея в `<Modal transparent statusBarTranslucent>`: отдельное окно поверх всего. Ринг — полноэкранный скрим (pointerEvents auto); активный звонок — root `box-none`, но Android-окно Modal всё равно перехватывает тачи: во время активного звонка UI за панелью заблокирован (как в Telegram/WhatsApp); back при активном звонке не уходит из экрана. Побочный эффект: uiautomator dump периодически не видит содержимое Modal (stale) — проверка UI звонка делается по пикселям скриншота (красная кнопка сброса #dc2626 ≈ 8000 px, зелёная статус-точка)
- Кнопки 📞/🎥 в шапке чата (`chats/[id]`) → `start(chatId, kind)`
- `expo-keep-awake` на время звонка (экран не гаснет в активном видео)

**Видео (этап 10)**

- Стор: `remoteCams: Record<string, VideoTrack | null>` и `localCam: VideoTrack | null` наполняются в `syncCams()`/`syncLocalCam()` на событиях `ParticipantConnected/Disconnected`, `Track{Subscribed,Unsubscribed,Published,Unpublished,Muted,Unmuted}`, `LocalTrack{Published,Unpublished}`; «живая» камера = трек подписан и `!pub.isMuted` (см. §9 про RN mute-trap). Появление/исчезновение локального трека синхронизируется и при внешних мутациях (LiveKit «скрытый» режим и т.п.)
- Видео-оверлей (`ActiveVideo` в `call-overlay.tsx`): direct — полноэкранная плитка собеседника + собственная PiP (110×165, `mirror`, по умолчанию top-right ниже шапки); групповой — сетка ≤ 8 плиток (2 колонки, своя — первой). Плитка без видео — аватар-заглушка с инициалами; если живых камер нет — хинт «Видео выключено у всех участников». PiP перетаскивается (PanResponder, прилипает к ближайшему горизонтальному краю) и обменивается местами с полноэкранной плиткой по тапу (тап = без движения < 3 px, иначе это драг)
- Управление (VideoControls): 🎙/🔇 (mute, как в аудио), 🎥/🚫 (toggleCam), 🔄 (switchCam — фронт/тыл через `LocalVideoTrack.setDeviceId()` по данным `enumerateDevices()`; в livekit-форке applyConstraints/facingMode переключение НЕ делает — см. §9; неактивна без камеры), 🔈 (динамик — для видео включён по умолчанию), 📵 hang-up; активные до `media === "connected"` заблокированы
- Терминология ринга: «Входящий видеозвонок» / «Видеовызов…», групповой баннер — «идёт видеозвонок · N уч.» (§17 веб: bug-parity — ринг-карточка рендерится до видео-ветки)
- Разрешение камеры — мягкий отказ: `ensureCamPermission()` (Android `CAMERA`) при start/accept/join видео; отказ → тост «Камера недоступна — только звук» (`err_cam_denied`), звонок продолжается как аудио. Отказ микрофона остаётся жёстким
- «Ответить без видео» (входящий видео-звонок): под кнопками ✕/📞 ринг-карточки пилюля `call.acceptNoVideo` → `accept(false)` — камера не запрашивается и не публикуется (только аудио-трек), включить можно потом кнопкой 🎥 (запросит разрешение и опубликует через republish). Веб-паритет реализован (та же пилюля в `CallOverlay.tsx`); аргумент прокидаётся через проп `accept={(withVideo) => …}` — если писать `accept={() => …}`, аргумент теряется и кнопка молча отвечает «с видео»
- Keep-awake — `activateKeepAwakeAsync` на время активного звонка (§17: обязательен для видео), `deactivateKeepAwake` в cleanup (mounted-flag паттерн)

**Ограничения MVP**

- Звонок живёт только пока приложение открыто (WS нужен для сигналинга): убили из recents → учасники видят leave; incoming-call при убитом приложении не доставляется (перспектива: FCM data `call.ring` + notifee CallStyle + foreground service — отдельный этап)
- Шаринг экрана на мобильном — не в MVP (Android 14 требует mediaProjection foreground-service — отдельно)
- Без интеграции с системным телефоном (ConnectionService/в стиле CallKit) — всё внутри приложения

## 4. Идентификация приложения

- `applicationId`: **`ru.vibe.chat.app`**
- `versionName` — семантическая (сейчас `1.0.1`), `versionCode` — монотонный счётчик (сейчас `2`; бамп при каждой release-сборке, синхронно в `app.json` и `android/app/build.gradle`); обновление — установка нового APK поверх старого (данные/кэш сохраняются), проверка `min_version` на старте (§3.8) заставляет обновиться

## 4.1 Релизная сборка (этап 8, реализовано 2026-11-26)

Пошаговый ранбук (предпосылки, бамп версий, keystore, сборка, проверка артефакта, установка/обновление, гейт e2e, раздача, грабли) — **`Docs/mobile-release.md`**. Здесь — только проектные решения:

- **Подпись**: release-keystore вне git (`android/app/keystores/`, пароли в `keystore.properties` рядом), бэкап обязателен вне репо (`~/.local/opt/keystore-backup/vibe-chat/`). Без properties release собирается БЕЗ подписи — молча подписать debug-ключом нельзя (смена подписи потом заблокирует обновления). Потеря keystore = потеря возможности обновлять приложение.
- **Версии**: бамп `versionCode`+`versionName` синхронно в `app.json` и `build.gradle` на каждой release-сборке; клиент сравнивает с `min_version` семантически, `versionCode` в гейте не участвует.
- **Cleartext/NSC** (`app/src/main/res/xml/network_security_config.xml`): release требует HTTPS по умолчанию (стенд — TLS везде); cleartext разрешён только dev-хостам: `localhost` (adb reverse), `10.0.2.2` (эмулятор→хост), `192.168.1.64` (LAN-IP хоста с dev-LiveKit, машинно-специфичен — при смене машины править XML). debug-оверлей `usesCleartextTraffic=true` перекрывается NSC.
- **Гейт версии (§3.8)**: при старте `GET /app/version` (без аутентификации) → если `min_version` задан и `versionName` клиента ниже — блокирующий экран «Требуется обновление» (без навигации и входа, кнопка «Проверить снова» пере-проверяет без рестарта; ссылка — `EXPO_PUBLIC_APP_DOWNLOAD_URL`, не задана — «обратитесь к администратору»). Fail-open: сервер недоступен или `min_version` пуст — приложение работает.
- **MINUS грабли env**: доступ к `process.env` — **только статический** (`process.env.EXPO_PUBLIC_X`). Babel-инлайнер Expo подставляет значения только для литеральных обращений; динамический `process.env['EXPO_PUBLIC_' + name]` в release-бандле = `undefined` (в debug его выручает рантайм-гидратация env от dev-сервера, в release её нет → «EXPO_PUBLIC_… не задан» при старте). Проверка запекания — в ранбуке §5.
- **Раздача**: APK с собственного keystore не требует ни Google Play/аккаунта разработчика, ни Google-аккаунта у пользователей — sideload («установка неизвестных приложений»); единственный Google-аккаунт — Firebase (FCM, уже есть).

### Ручной тест-план (регресс перед каждой release-сборкой)

1. Логин (ROPC) валидные/невалидные креды; регистрация инвайт-код; регистрация в открытом режиме
2. Logout → полный выход; вход вторым пользователем → данные первого не видны (пуш-токен отвязан, кэш чист)
3. Отправка текста; идемпотентность: ретрай при таймауте не создаёт дубль (`client_ref`)
4. Airplane mode: отправка → ошибка → «повторить» после включения сети; перезапуск в оффлайне → лента из кэша
5. Realtime: два устройства — доставка < 1 с, typing, presence, реакция у собеседника видна
6. Пагинация: скролл вверх загружает историю; `updated_after` восстанавливает ленту после реконнекта
7. Вложения: фото через Picker, прогресс, отмена, превью, blurhash; файл > лимита отклонён
8. Пуши: оффлайн-получатель получает пуш; foreground — без уведомления; тап из cold start → чат
9. Отказ `POST_NOTIFICATIONS` → приложение работает, пуши не приходят
10. Тема светлая/тёмная/системная применяется сразу; язык — из словаря (нет хардкод-строк)
11. Deep link из уведомления в удалённый чат → fallback список + snackbar
12. Удаление сообщения → плашка «удалено у всех» у обеих сторон; реакции на удалённом скрыты
13. `min_version`: старая версия → блокирующий экран

## 9. Решённые вопросы

- **Пуши — FCM, решение зафиксировано.** Альтернатива (UnifiedPush/own push-шлюз) рассматривается только если корпоративные ограничения на Google-сервисы ужесточатся.
- **Оффлайн-режим нужен**: загруженные данные (сообщения, картинки и т.п.) должны сохраняться между запусками. Реализация — персистентный кэш (MMKV для мелких данных + кэш медиа на файловой системе поверх presigned GET); TanStack Query с persister даёт базу. Кэш сообщений — этап 3, медиа-кэш — этап 5 (§8).
- **iOS не планируется** на MVP; выбор Expo сохраняет возможность позже без смены стека.
- **Версионирование API** — по мере необходимости: `/api/v1` уже есть, обратная совместимость соблюдается в рамках обычных изменений. Специальных механизмов (слотирование версий, freeze) на MVP не вводим.
- **WS-реконнект не плодит соединения (этап 4, e2e)**: сокет присваивается в модульной переменной ДО навешивания хендлеров; `onclose` проверяет `socket !== ws` и игнорирует закрытие заменённого сокета — иначе каждый реконнект оставлял висящий старый сокет, сервер плодил connection'ы (видно в uvicorn-логе: череда `POST /ws/ticket` + `WebSocket ... [accepted]` без закрытий).
- **WS `message.*` приходит обёрнутым (этап 4, e2e)**: бэкенд публикует payload как `{message: <MessageOut>}` (§9 концепции), клиентский `asMessage` разворачивает `data.message ?? data` — без этого все live-события молча отбрасывались (доставка работала только через refetch/catchUp).
- **Presence-heartbeat на бэкенде (этап 4)**: `presence_touch` объявлен, но нигде не вызывался — ключ протухал через 60 с при живом WS; в `ws_endpoint` добавлена задача `_presence_heartbeat` (touch каждые 30 c, включена в `asyncio.wait` + cancel в finally).
- **Optimistic-отправка мержится по `client_ref` (этап 5, e2e)**: локальное сообщение обязано нести `client_ref` = Idempotency-Key, и ключ генерируется один раз вызывающим (передаётся через variables мутации) — `onMutate` и `mutationFn` используют один ключ; иначе серверный ответ/WS-событие не находят локальную запись и статус навсегда «Отправка…».
- **`asset.fileSize` из Photo Picker врёт (этап 5, e2e)**: `content://` → blob другого размера (у тестового фото подписали 13805, факт — 11821) → S3-подпись требует точного Content-Length → 403 SignatureDoesNotMatch. Размер для upload-url берётся **только** из `blob.size` (fetch до upload-url). Content-Type в presigned PUT не подписывается (XHR мог слать другой CT; реальный mime определяет sniffing при complete) — `presign_put(storage_key, size, ttl)`.
- **Лимит 100 МБ — двухступенчатый (этап 5)**: pre-check по `asset.fileSize` ДО fetch (fetch 108 МБ `content://` в RN падает «Network request failed» — Blob memory-backed), точная проверка по `blob.size` после fetch. Без pre-check большой файл падает с неинформативной сетевой ошибкой вместо FileTooLargeError+Alert.
- **Эмодзи-реакции — имена, не символы (e2e)**: API хранит имена (`thumbs_up`/`heart`/`laugh`/`fire`/`check`, сверка с `ALLOWED_EMOJI` на бэкенде); веб так и отправляет. Мобильный клиент изначально отправлял Unicode-символы («👍») → 422. Контракт: клиент отправляет имя, чипы рендерят `EMOJI_CHAR[name] ?? name`.
- **Лайтбокс — только Modal (e2e)**: полноэкранный просмотр картинок как plain absolute View внутри Stack-экрана рендерится поверх ленты, но тач по фону (закрытие) не получает — Pressable внутри «пустого» оверлея не срабатывает. Решение — `<Modal transparent>` (как контекстное меню чата): отдельное окно, тачи гарантированы; заодно «×»-кнопка не нужна — закрытие тапом по фону или back (onRequestClose).
- **Logout обязан чистить MMKV-кэш (e2e)**: `clearCacheStorage()` существовал, но не вызывался — оффлайн-кэш чатов/сообщений переживал выход, следующий пользователь на устройстве получал 403 при догонянии чужих чатов (и видел хвосты в оффлайне). Вызов добавлен в `logoutLocal` (§3.2).
- **Data-only FCM + headless JS (этап 7, e2e)**: бэкенд шлёт только `data` + `android.priority=high` — notification-часть рисует системное уведомление, не поднимая headless JS (нет нашей агрегации/deep link; на эмуляторе вообще не отображалась). Headless-обработчики (`messaging().setBackgroundMessageHandler`, `notifee.onBackgroundEvent`) регистрируются в `mobile/index.js` (main в package.json) на top-level ДО AppRegistry — иначе `No task registered for key ReactNativeFirebaseMessagingHeadlessTask` и процесс, поднятый FCM, молча ничего не делает. Тап по уведомлению отдаёт notifee (не RN Firebase): RN Firebase `getInitialNotification`/`onNotificationOpenedApp` работают только для notification-сообщений.
- **«Закрыто» ≠ force-stop (этап 7, e2e)**: `adb shell am force-stop` блокирует доставку FCM broadcast'а (`GCM broadcast intent callback: result=CANCELLED`) до следующего явного запуска; честный сценарий — свайп из recents (процесс убит, broadcast-приёмка сохраняется) или `am kill` (не убивает процесс с живой активностью). Проверка доставки: `logcat` фильтр `c2dm|HeadlessTask|NOTIFEE`.
- **WS-SDK сборки (этап 7)**: в WSL нужен полный Android SDK (`~/.local/opt/android-sdk` через cmdline-tools: `platforms;android-35`, `build-tools;35.0.0`, `ndk;27.1.12297006`, JAVA_HOME=jdk17); `~/.local/opt/platform-tools` — это только adb, он не SDK (до этого этапы собирались… на деле сборка dev-APK впервые потребовала полный SDK).
- **Двустороннее аудио на эмуляторе — включать микрофон хоста (этап 9, e2e 2026-11-25)**: эмулятор по умолчанию подаёт в приложение тишину (виртуальный микрофон): трек публикуется, но абонент не слышит. Включается в окне эмулятора: Extended Controls → Microphone → «Virtual microphone uses host input» (+ Windows: Параметры → Конфиденциальность → Микрофон → классические приложения). После включения — полный двусторонний сценарий с веб-пиром подтверждён пользователем (§8). Выход эмулятора (звук из хоста) работает без настроек.
- **Заморозка UI после простоя (этап 9, инцидент 2026-11-25, причина не найдена)**: после ~30 мин простоя приложение перестало рендерить (экран статичен 5+ мин: пиксельно идентичные скриншоты, тапы обрабатываются, WS-соединение живо по presence), при этом JS-поток не мёртв (~5% CPU), logcat ReactNativeJS молчит. Лечится force-stop. На здоровом состоянии не воспроизводится (cold start → сессия восстановилась, WS работает). Если повторится: до рестарта снять `adb shell kill -3 <pid>` (ANR-трейсы) и logcat; подозреваемые — WS-heartbeat/таймеры после истечения access-токена.
- **Переключение камер (фронт/тыл) на реальном устройстве — setDeviceId, не applyConstraints (этап C, e2e 2026-11-26, Xiaomi)**: в livekit-форке react-native-webrtc `applyConstraints({facingMode})` на живом треке камеру НЕ переключает — `CameraCaptureController.applyConstraints` сознательно берёт `constraintFacingMode` из НАЧАЛЬНЫХ constraints («constraint violation to change these through applyConstraints»), т.е. свитч молча превращается в no-op (симптом: нет новых `Camera2Session: Create new camera2 session` в logcat, пиксели не меняются). `_switchCamera()` — не выход: в форке это просто обёртка над тем же applyConstraints. Рабочий путь: `navigator.mediaDevices.enumerateDevices()` на Android отдаёт videoinput с `deviceId` (= строковый индекс камеры) и `facing` (`"front"|"environment"`) → противоположный по facing девайс → `LocalVideoTrack.setDeviceId(id)` (livekit-client): внутри restartTrack + replaceTrack, тот же sid, без пересогласования, короткое подмерзание ~1 c. e2e: тап 🔄 → `Create new camera2 session on camera 1 → camera 0 → camera 1` (свитч туда-обратно), PiP телефона меняется радикально (diff mean 99), декодер собеседника продолжает тикать; у собеседника при replace трека наблдался `signalReconnecting -> connected` (восстановился сам). Тылушка при лежащем телефоне снимает стол — пиксельный diff remote-картинки до/после ≈ 0 при реальном свитче: доказывать свитч по logcat Camera2 + локальному PiP, не по remote-картинке.
- **uiautomator врёт при живом видео (этап C, 2026-11-26)**: во время активного видеозвонка `uiautomator dump` может вернуть устаревшее a11y-дерево (элементы фазы ринга поверх фактически работающего звонка) или упасть с `could not get idle state` (непрерывный рендер не даёт idle). Экран врать не умеет: сверять состояние по `screencap` + пиксельному анализу (красная кнопка hang-up, зоны PiP/peer), а dump использовать только на статичных экранах.
- **Metro-refresh во время звонка ломает стор звонков (этап C, 2026-11-26)**: fast-refresh в активном звонке (правка модулей, которые импортирует calls-стор/оверлей) пере-создаёт zustand-сторы — current=null, оверлей размонтируется, а WS-события могут достать в пере-инициализированный стор (`call.ring` по тому же id откатывал активный звонок в ringing — «фантомная ринг-карточка» поверх живого звонка; защита в `handleWsEvent`: ring для уже активного звонка игнорируется). Для dev-тестов звонков: правки кода — только между звонками, после правок — холодный рестарт обоих устройств.
- **Тост ошибки звонка — авто-скрытие (этап 9, e2e)**: `error` в `calls.ts` жил до следующего действия (инцидент: тост «Не удалось выполнить звонок» после 401 при истёкшем токене висел поверх ринг-карточки, пока пользователь что-то не нажмёт). Все установки ошибки сведены в `setErrorState()` — таймер 4 с гасит тост, если та же строка ещё актуальна; проверено e2e (тост «Медиа-сервер недоступен» при остановленном LiveKit виден на +7 с, исчез на +13 с, карточка звонка не задета).
- **RN mute-trap камеры — включение через unpublish+republish (этап 10, e2e 2026-11-25)**: на RN-адаптере `setCameraEnabled(false)` глушит капчер на нативе (сервер LiveKit помечает трек muted по отсутствию RTP), а обратный `setCameraEnabled(true)`/`track.unmute()` (`_mediaStreamTrack.enabled = true`) капчер НЕ возрождает — сервер навсегда видит `muted: True`, клиент — мёртвый трек (e2e: PiP не возвращался, красная кнопка не гасла, JS-ошибок в logcat нет; lk_parts.py подтвердил stuck-muted). Надёжное включение камеры: `unpublishTrack(pub.track)` (в try/catch — трек может быть уже мёртв) + `setCameraEnabled(true)` → создаётся и публикуется свежий трек; `syncLocalCam` подхватывает его по `LocalTrackPublished`. Выключение — обычный mute. Поэтому UI-синхронизация камеры проверяет `pub.isMuted`, а не существование publication (mute не удаляет publication).
- **Задержка видео на эмуляторе ~1–1.3 c — норма для dev-топологии (этап 10, измерения 2026-11-25)**: glass-to-glass «камера телефона → экран эмулятора» ≈ 1 с (по поворотам виртуальной сцены: расхождение моментов смены уровня на записях обеих сторон ~1.3 c минус скью запусков screenrecord). Доминанта — **приёмный видео-jitterBuffer эмулятора = 1.05 c** (адаптивный: раскручивается из-за фризов декодера): goldfish VP8-декодер переваривает только 11 fps из ~24 входящих (42% кадров дропается, 28 фризов на ~11 c за ~2 мин), композитор эмулятора отдаёт ~5–6 fps. Сеть НЕ виновата: RTT 5–16 мс даже через TURN, потери 0, jitter 31 мс. Источник цифр — приложение само логирует `'webrtc stats'` в logcat каждые 30 c (inbound: jitterBuffer/fps/framesDropped/freezeCount; publisher: RTT) — готовый инструмент диагностики задержки. На реальных устройствах (HW-кодеки, без slirp/TURN-обходов) ожидаемые 150–400 мс; целенаправленно не оптимизировать — золотфиш-декодер артефакт эмулятора. Замер через screenrecord ненадёжен: PTS записей дрейфуют на 5–15% (дроп кадров растягивает таймлайн), точность ±1.5 c — для точных замеров только webrtc-статистика.
- **Republish камеры удалённой стороны убивает локальный видео-трек эмулятора (этап 10, e2e 2026-11-25)**: когда собеседник выключил камеру и включил обратно (клиентский toggleCam = unpublish+republish свежего трека), локальная камера эмулятора исчезла на SFU (у участника остался только аудио-трек; свой PiP → аватар). Восстановление — локальный toggle 🎥 OFF→ON (свой republish), проверено. Экранозапись screenrecord подозревалась, но не подтвердилась (камера пережила 60-секундную запись с 4 поворотами сцены). Разбирать лениво: артефакт только на эмуляторе, на реальных устройствах не воспроизводился.
- **Виртуальная камера эмулятора — статичная сцена (этап 10, e2e)**: скриншоты/экранозаписи PiP-плитки пиксельно идентичны кадр в кадр, хотя рендеринг живой (logcat `Camera fps`, `EglRenderer … Rendered: N`, счётчик буферов SurfaceFlinger растёт). Это артефакт эмуляторной «виртуальной сцены» (лапша фикуса не шевелится), а не баг клиента. Движение доказывается поворотом окна: `adb emu rotate` → кадры плитки расходятся (diff > 20). Не чинить «замороженное видео» в эмуляторе — проверять живость рендера, а не смену картинки.
- **Перетаскиваемый PiP + тап-обмен местами (этап 10, e2e 2026-11-25)**: PiP (110×165) тапом меняется местами с полноэкранной плиткой (`useSwapped` per-callId, зеркала пересчитываются: своё видео зеркалится только на фронтальной камере, чужое — никогда), драгом перемещается и прилипает к ближайшему горизонтальному краю. Грабли: `PanResponder.create` в `useRef` замыкает колбэки на ПЕРВЫЙ рендер — `props.onSwap` из замыкания ставил одно и то же значение стейта (первый тап срабатывал, все последующие после драга «умирали»); актуальный колбэк держим в ref (`onSwapRef.current = props.onSwap` в теле компонента). Драг работает и без фикса — он читает `boxRef`; проверка тапа именно ПОСЛЕ драга обязательна.
- **«Ответить без видео» (этап 10, e2e 2026-11-25)**: `accept(withVideo)` — при `false` камера не запрашивается и не публикуется (сервер видит только аудио-трек), PiP скрыт, кнопка 🎥 в красном состоянии; последующее включение камеры в звонке работает (запрос разрешения + republish). Грабли: (1) проп-обёртка `accept={() => void accept()}` теряет аргумент — кнопка «без видео» молча отвечает «с видео», нужен `accept={(withVideo) => void accept(withVideo ?? true)}`; (2) debug-сборка берёт JS из Metro — после правок стора недостаточно переставить APK, нужен холодный старт при свежем Metro (иначе прежний бандл); (3) `adb shell pm revoke` **убивает процесс приложения** — звонок/ринг пропадают, телефон остаётся на лаунчере: перед revoke останавливать тест, после — запускать приложение заново.
- **Двух-устройственный видеозвонок (эмулятор + телефон) — network-топология (e2e 2026-11-25)**: слёрп эмулятора **не пропускает UDP на собственные IP хоста** (10.0.2.2 и LAN-адрес Windows — пакеты теряются; UDP в интернет и на eth0 WSL (172.17.192.0/20) ходит симметрично; TCP-туннели adb reverse работают всегда) → srflx от Google-STUN даёт «публичный» адрес, до которого сервер за NAT не достучится (hairpin NAT не работает), и ICE падает через ~15 с (janitor выкидывает участника). Диагностика: `getprop net.dns1` + `ping google.com` (пустой DNS ломает и srflx — лечится только полным рестартом эмулятора), `ICE candidate pair stats` в логах LiveKit (requestsSent/responsesReceived), `lk_parts.py`. Решение — dev-coturn с `external-ip=WSL eth0` (сервис `coturn` в compose, см. §3.12) + `rtc.turn_servers`/`stun_servers` в livekit.yaml: эмулятор берёт TURN/STUN с WSL-адреса, телефон и браузер идут напрямую на node-ip. toybox-nc на Android: флаги ТОЛЬКО до позиционных аргументов (`nc -u -w 4 HOST PORT`), иначе «bad argument count» и проба молча не отправляется. Кнопка «Завершить» в видео-оверлее эмулятора — (1004,2123); тап рядом (894,2122) — мёртвая зона: оверлей закрывается без POST /leave → у собеседника зомби-звонок (плюс stale ринг-карточка), лечится REST /leave всем участникам.
